> **venv 路径不能含非 ASCII 字符。** mediapipe 的 native 层按单字节路径打开 graph 文件，
> 路径带中文（包括放在 `D:\桌面\…` 下）会报 `The path does not exist`，**但文件明明存在**。
> 我做过对照实验：同一项目目录 + ASCII 路径 venv → 正常。
> 结论：**项目目录可以带中文，venv 不行。** 请统一 `C:/venvs/photocheck`。
>
> 你们的 `D:\Program Files\PhotoCheck\venv` 是 ASCII，没问题。

## 4. 接口

```python
from core.detect import analyze, probe_region, classify, detector_status

result = analyze("express_001.png", "express_001")
# AnalysisResult: .image_descriptor / .detections / .warnings / .timings_ms / .to_json()

probe_region(image_or_path, [x, y, w, h])   # → RegionProbe：区域内"还检出什么"，不是 passed/failed
classify(payload)                   # → QRClass(subtype, risk, summary, note)，纯规则不联网
detector_status()                   # → {"ocr": "ok", "qr": "ok", "face": "unavailable"}
```

三个检测器都是 `f(image, roi=None) → 结果` 的**纯函数**，没有跨调用状态。
这是 K-09b/K-09c 能对已遮区域独立重跑的前提。

## 5. ⚠️ 你们的 `a_contract.py` 还带着两个缺陷

你们第 4.1 节写"保留 A 自己的严格校验，包括：手机号和身份证掩码格式"。
那份掩码规则来自 `框架.py`，而它有两个已知问题，已在 2026-11-02 的评审中修复：

| 缺陷 | 触发条件 | 后果 |
|---|---|---|
| 身份证掩码正则结尾写死 `\d{4}` | 证件末位是 X（真实证件约 1/11） | 整条 Detection 构造失败 |
| 长数字串规则删分隔符后判定 | EXIF `datetime` / `serial` 的 `masked_preview` | 日期被当成未掩码，meta 全挂 |

在你们仓库里跑下面这段就能确认（20 秒）：

```python
from photocheck.detectors.a_contract import Detection
# 期望：通过。若抛 ContractError → 未同步
Detection(id="d1", image_id="i1", kind="text", subtype="idcard",
          bbox=(1,1,10,10), detector_score=0.9, risk=3,
          details={"masked_preview": "1101**********001X", "idcard_check": "pass"})

# 期望：通过。若抛 ContractError → 未同步
Detection(id="d2", image_id="i1", kind="meta", subtype="datetime",
          bbox=None, detector_score=None, risk=1,
          details={"masked_preview": "2024-06-01"})
```

修复点（与 `core/contract.py` 一致）：

```python
_IDCARD_MASK = re.compile(r"^\d{4}\*{10}(?:\d{4}|\d{3}X)$")   # 允许末位 X
# meta 的启发式改成在原始串上判断，不删分隔符：
_UNSAFE_RAW_DIGITS = re.compile(r"\d{7,}")
```

改完这两处，你们的契约与 A 的产出才真正对得上。**否则 X 结尾的证件会在你们侧整条丢失**，
而且不会报错——`warnings` 里只有一行，端到端测试反而是绿的。

## 6. 关于 `express_001.json` 的 warning 差异

上一包样例里有"人脸不可用"的 warning，是因为生成它的 venv 在中文路径下。
本包的样例跑在 ASCII venv，人脸可用，因此：

```json
"warnings": []
```

如果你们的用例断言"必有 warning"，请改成断言结构而不是数量：

```python
assert isinstance(envelope["warnings"], list)   # ✅
# assert envelope["warnings"]                    # ❌ 人脸可用与否是环境属性，不是契约属性
```

另外，样例里的 `timings_ms` 是**冷启动**（含模型加载，约 5.9 s）。
预热后的 T_ocr 中位数本轮实测 **1640.5 ms**（`reports/t_ocr_baseline_20261106_2036.json`），
历次测量落在 1640~1716 ms 之间（本机抖动约 ±3%），README 里取偏保守的 **1686 ms** 作基线。
K-03 的 W4 验收线按 1686 ms 计为 `T_ocr × 1.2 = 2023.6 ms`。**不要把样例里的数字当基线**。

## 7. 已知限制（写进报告时不能越界）

- 同 OCR 复检只能证明"同一检测器本次不再读出"，**不能证明人眼不可读**（K-09 边界，R-03/R-04 才回答）
- 二维码解不出时只给框，subtype 记 `qr_unknown` / risk 1
- 人脸只给区域，`details` 为空；侧脸、口罩允许漏
- `+86` / `0086` 前缀的手机号**不匹配**（已知，`badcases/BC-0005`，等数据集决定是否支持）
- **一维条码不支持**：pyzbar 的 libzbar DLL 在本机加载失败，实际走 cv2 兜底，而 cv2 只解二维码
  （`badcases/BC-0008`，`open`）。`detector_status()["qr_backend"]` 会报 `cv2`，请勿据此认为条码可用
- 人脸不可用时 `probe_region` 的 `residual_face` 恒为 0，**不能**当作"该区域没有人脸"的证据
- 当前召回数字来自 4 张自造合成图，`reports/基线表_v0.md` 表 A 的 100% **不可对外引用**

## 2026-11-06 修订（对应《后续推进计划》§2 / §5 / §6 / §7）

1. **requirements.txt 全 ASCII**，OpenCV 统一为 `opencv-contrib-python==4.10.0.84`，

3. **重写 BC-0007 静区测试**：不再断言"外扩归零必然解不出"（那是解码器的属性），
   改为后端无关的三条不变量 + `_expand_for_quiet_zone` 的纯几何断言。
4. **代码转英文**：注释、docstring、异常消息、`warnings`、控制台输出全部 ASCII，
   本轮补齐了 `core/eval.py` / `core/badcase.py` / 6 个 `scripts/` / 8 个 `tests/`。
