## 指标定义（与 C 的评测协议必须一致）

**匹配分两级，不要合成一个数**：

| 级别 | 定义 | 回答什么 | 对应卡 |
|---|---|---|---|
| 几何命中 | 同 `kind` 且 bbox 的 IoU ≥ 0.5 | 有没有找到这个东西 | K-03 / K-05 / K-07 |
| 类型正确 | 命中的框里 `subtype` 也一致 | 找对了它是什么 | K-04 / K-06 |

| 指标 | 定义 |
|---|---|
| 几何召回 | 几何命中数 / 真值数 |
| 类型召回 | 类型正确数 / 真值数 |
| 漏检 | 有真值但无任何检出（几何未命中） |
| 误报 | 无真值却报出的条数，单位 **处/张**（验收线 ≤2） |
| 精确率 | 几何命中数 / 全部检出数 |

> **v0 的口径是错的，已废弃**：v0 写"同一 subtype 且 IoU≥0.5 视为命中"，把两级合成一级。
> 后果是「框住了但判成 `qr_unknown`」会同时扣掉召回和精确，看起来像检测器坏了，
> 实际只是分类错了 —— 归因错了就不知道该修 K-05 还是 K-06。`tests/test_eval.py`
> 里 `test_subtype_mismatch_is_geometry_hit_but_type_miss` 锁住了这个口径。

### ⚠️ IoU 阈值敏感度：换个阈值，召回从 100% 掉到 60%

实测真值框与检测框的 IoU 分布（同一批检测结果，一个字都没改）：

| 图像 | subtype | IoU |
|---|---|---|
| express_001 | phone | 0.894 |
| express_001 | idcard | **0.553** |
| idcard_001 | idcard | **0.541** |
| express_001 | qr_link | 0.762 |
| qr_wifi_001 | qr_wifi | 0.766 |

- 当前阈值 **0.5** → 几何召回 **100%**（5/5）
- 换成 **0.6** → 几何召回 **60%**（3/5），`idcard` 全掉
- 不是检测退化了，是**口径变了**

原因：文字框是扁长的（身份证号码框约 216×15 px），**高度差 5 px 就能让 IoU 掉 20% 以上**。
GT 来自 `textbbox`（含 ascent/descent），检测框紧贴 ink，两者高度天然有差。

所以 `KIND` 不同应该考虑不同匹配规则：

| kind | 建议匹配规则 | 理由 |
|---|---|---|
| text | 中心点落在 GT 框内 + 水平重叠 ≥ 0.5，或 IoU ≥ 0.4 | 扁长框对高度误差过敏 |
| qr / face | IoU ≥ 0.5 | 近方形，IoU 稳定 |

**这必须由 C 定，不能由 A 单方面改**——否则 A 报 100%、C 算 60%，会变成互相指责。
已列入「待对齐」第 5 项。

### 测量方法会决定结论 —— 这一节比数字重要

同一台机器、同一批图、同一天，三种测法给出三个数：

| 测法 | text 中位 | 结论会变成 |
|---|---|---|
| 不预热（含冷启动） | 4583.8 ms | "超标 2.2 倍，K-03 挂了"（**假**） |
| 只预热第一张图 | 3157.1 ms | "超标 1.5 倍"（**假**，每图尺寸不同，各有首跑开销） |
| **每图预热 + 单次** | **1775.7 ms** | 接近真值 |
| **每图预热 + 5 次取 min（bench）** | **1686.3 ms** | 作为 T_ocr |

> 规律：**RapidOCR 的推理开销与输入尺寸相关**，换尺寸的第一张图仍会偏慢
> （900×620 首图 5.1s vs 同尺寸稳态 2.0s）。所以跨图评测必须**每图预热**，
> 而 T_ocr 这种验收数必须**同图多次取 min**。
> `scripts/eval_detect.py` 默认 `--warmup 1`（每图一轮）；它的耗时列只用于看趋势，
> 验收一律以 `scripts/bench_ocr.py` 为准。

另：T_ocr 在 11-02 与 11-06 两次实测为 1715.8 / 1686.3 ms，漂移 1.7%。
验收线是 ×1.2（即 20% 余量），而机器状态本身的波动已经吃掉近 2%，
所以**验收必须在同一台机器、同一时段、同参数下对照跑**，跨天比较没有意义。

## 怎么跑

```bash
PY=/c/venvs/photocheck/Scripts/python.exe

# 指标（默认 samples/gt + samples/synthetic，每图预热 1 轮）
$PY scripts/eval_detect.py
$PY scripts/eval_detect.py --json reports/eval.json --md reports/eval.md
$PY scripts/eval_detect.py --kinds text,qr        # 不评人脸
$PY scripts/eval_detect.py --strict               # 有漏检/误报 → 退出码 1（CI 用）

# 真值从哪来：make_sample.py 在画图时用 textbbox 记录，不是从检测结果反推
$PY scripts/make_sample.py

# 耗时基线
$PY scripts/bench_ocr.py samples/synthetic --repeat 5

# 案例库
$PY scripts/badcase_index.py --check
```

**真值不得从检测结果反推**。用检测输出当 GT，召回永远是 100%，这种基线表比没有更危险。
所以 `make_sample.py` 在绘制时用 `ImageDraw.textbbox` 记录坐标，GT 文件里也不存号码明文。

## 怎么对比两次提交

```bash
# 提交前存快照
$PY scripts/eval_detect.py --json reports/eval_<tag>.json
$PY scripts/bench_ocr.py samples/dev --repeat 5 --out reports/t_ocr_<tag>.json
$PY scripts/badcase_index.py
```

对比时必须同时看四件事，只看一项会得出错误结论：

1. **T_ocr 是否超过 2023.6 ms** —— 超了就是 K-03 验收失败，不是"稍慢一点"。
2. **几何召回是否下降** —— 召回掉 5% 而速度提升 2 倍，是拿检出换速度，不算改进。
3. **类型召回是否下降** —— 几何召回没变但类型召回掉了，说明分类规则退化（K-06）。
4. **badcase 是否新增** —— 比任何指标都灵敏，指标只在样本上体现，badcase 会立刻暴露。
