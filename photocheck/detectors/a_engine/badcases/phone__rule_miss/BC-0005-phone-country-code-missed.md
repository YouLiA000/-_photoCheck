## 现象

| 输入 | `find_entities()` |
|---|---|
| `手机 +8613800138000` | `[]` |
| `+86 13800138000` | `[]` |
| `电话:+86-138-0013-8000` | `[]` |
| `Tel: 0086 138 0013 8000` | `[]` |
| `联系人 13800138000` | `[('phone', '13800138000')]` ✅ |

凡是带国际区号的写法，一个都识别不出来。

## 复现

```bash
C:/venvs/photocheck/Scripts/python.exe -c "
import sys; sys.path.insert(0,'.')
from core.detect.entities import find_entities, normalize_with_index
for t in ['+86 13800138000', 'Tel: 0086 138 0013 8000']:
    print(repr(normalize_with_index(t)[0]), '->', find_entities(t))
"
```

## 根因

`PHONE_RE = r"(?<!\d)1[3-9]\d{9}(?!\d)"`。

归一化删掉空格和横线后，`+86 138 0013 8000` 变成 `+8613800138000`。
号码首位的 `1` 前面紧邻区号末位 `6`，`(?<!\d)`（左边不能是数字）直接失败，
整串不匹配。`0086` 同理。

这个环视断言本身是对的——没有它，`202613800138000` 这种长串会被从中间切出一个假号码。
问题在于断言没有把"合法的区号前缀"排除在外。

## 当时为什么挂起

1. 规格卡原文只要求「两侧非数字，允许空格横线」，没有明写国际区号，严格说属范围外。
2. 放开断言会同时放开负样本：快递单上的 `0086` 开头订单号、`8613` 开头的运单号
   都可能被切成假号码，误报率会上升。误报 ≤2 处/张是硬验收线。
3. 需要 C 的 dev 集里带区号正样本的占比，没有这个数改与不改都是猜。

## 处置

改成显式枚举区号，而不是"把前面的数字放开"：

```python
PHONE_RE = re.compile(r"(?<!\d)(?:(?:\+86|0086)1[3-9]\d{9}|1[3-9]\d{9})(?!\d)")
```

- 区号只认 `+86` 和 `0086` 两种写法，`8613…` 这种裸 86 不认——这正是当初担心的
  误报来源，不放开就不会有。
- 左侧 `(?<!\d)` 保留，`202613800138000` 这类长串仍不会被切出假号码。
- 匹配区间包含区号，所以 K-08 的遮盖框会把 `+86` 一起盖住；否则号码被遮盖了，
  区号还留在图上。

验收：

| 输入 | 结果 |
|---|---|
| `+8613800138000` | `phone`，`138****8000` |
| `0086 138 0013 8000` | `phone`，`138****8000` |
| `＋８６ １３８ ００１３ ８０００`（全角） | `phone`，`138****8000` |
| `订单号 00861380013800`（少一位） | 不报 |
| `序列号 008678012345678`（非手机号段） | 不报 |
